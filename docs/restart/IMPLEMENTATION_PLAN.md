# Ordered implementation plan

Stage 0 established the safe boundary and proposal. Stages 1 and 2 are implemented as separate, reproducible data layers; later stages remain proposals.

| Stage | Work and dependency | Tests and completion gate |
| --- | --- | --- |
| 0 — safe restart | Checkpoint HEAD and working tree; inventory ignored evidence; audit jobs; archive historical reports/handoffs; retire old public CLI and obsolete scripts; keep the open notebook dependency isolated. | Bundle and manifest verify, unaffected notebook tests pass, no abandoned job active, no advertised stale CLI. |
| 1 — source collection | **Implemented in Stage 1.** See [Stage 1 handoff](stage1/HANDOFF.md), [API contracts](stage1/STEAM_API_CONTRACTS.md), and [schema](stage1/RAW_DATA_SCHEMA.md). | Four-game bounded collection, fixture tests, and coverage report are the completion gate. No change extraction, matching, labels, or training. |
| 1.5 — multilingual audit and collection correction | **Implemented after auditing live Stage 1 evidence.** See [`MULTILINGUAL_AUDIT.md`](stage1/MULTILINGUAL_AUDIT.md) and the [language coverage report](../../reports/relevance_v1/stage1/latest/language_coverage.md). Confirm the API filter used, add configurable language filters with an `all` default, preserve source language/text, isolate filter checkpoints, and report counts by game and patch window. Existing windows already used all languages, so do not recollect them for language coverage. | Tests cover `['all']`, explicit filters, filter-safe resumability/deduplication, Unicode round trips, mixed text, language coverage and metadata quality. Report incomplete windows as collection-depth gaps, not language-filter gaps. |
| 2 — patch changes and review claims | **Implemented.** See [`stage2/HANDOFF.md`](stage2/HANDOFF.md), [architecture](stage2/ARCHITECTURE.md), and [data contracts](stage2/DATA_CONTRACTS.md). Classify announcements, preserve linked note URLs, extract structured changes and exact review claim spans, build per-game vocabulary, and encode temporal overlap without assigning relevance. | 70 tests pass; full snapshot build is reproducible; sampled source spans validate exactly; extraction gaps and the manually inspected sample are documented. No candidate pairs or labels. |
| 3 — full-list relevance pilot and multilingual retrieval | Pick a large patch with a complete change list and adequate post-patch coverage. Draw about 300 reviews using a fixed seed from the complete eligible population, independent of retrieval. Compare multilingual embeddings with lexical and entity-based retrieval; include non-English reviews matched to English change text. Translate only when error analysis warrants it. | Keep full-list relevance judgments as reference evidence; report retrieval separately per language and cross-language pair, include sample sizes and uncertainty, validate exact quotes and change IDs, and never turn uncertain into negative. |
| 4 — multilingual LLM decisions and evaluation | Use multilingual LLM labeling where supported, requiring exact quotes from original-language review text. Keep machine-generated labels separate from independently verified judgments. Analyze missed links, broad changes, language ambiguity and cross-patch contamination; add independent second passes on stratified samples. | Patch/game held-out split, leakage checks, metrics by review and change language, cross-language pairs, retrieval miss audit, error slices and uncertainty. Qualify machine-reference labels; report insufficiency instead of training if positives are too sparse. |
| 5 — operational hardening | Add repeatable offline runs, CI tests, versioned schemas and reproducible manifests. Preserve language-sliced quality metrics and drift checks. Consider model serving and registry/data versioning only after stable contracts, evaluation and a real user-facing query flow. | Rebuild from frozen inputs, validate release candidate, monitor source and language coverage, document rollback. Select DVC/MLflow/deployment only when actual operational needs justify them. |

Priorities are evidence quality, source coverage and reproducible sampling. The previous lexical candidate pool is historical diagnostic data only. Patch-window coverage is a reportable sampling attribute, not a hard screening step that makes potentially relevant reviews invisible. The user has no human annotation team, so LLM decisions are silver data; evaluation must say exactly what independent checks were done and must not call those labels gold.

Stage 0 resolved the open-notebook dependency by retaining the legacy package and notebook as an isolated historical island. Stages 1, 1.5, and 2 use separate imports, paths, identifiers, and commands; later stages must preserve that boundary. Stage 2 extraction is complete; relevance pairing, judgments, and model training have not started.
